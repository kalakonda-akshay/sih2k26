01

What was built

A logistics and road-accessibility intelligence platform for the eight North Eastern states, built on Convex as the sole backend. Sixteen routes, twenty-two backend modules, and five intelligence engines — all running against live data.

The design rests on one reframe. Logistics in the North East is not a route-optimisation problem on a dense graph; it is a survivability problem on a sparse one. Between most district pairs there are one or two viable corridors, so when a landslide closes a single cutting the alternative is hours longer or does not exist. The atomic unit is therefore the road segment, and the primary question is whether it will still be passable.

Command centre

Nine live KPIs

One reactive query feeds every card, so the numbers cannot disagree with each other.

Map

Five layers

Vehicles, incidents, roads, AI risk zones, weather — filterable, clusterable, click-to-fly.

Risk

Six weighted factors, every point attributable to a named input with a stated reason.

04

Algorithms

Seventeen named algorithms across five engines. None is a trained model; all are deterministic and reproducible, which is the property that makes a government decision-support system auditable.

Graph & routing

Dijkstra's shortest path
convex/lib/routeGraph.ts · findShortestPath

Single-source shortest path over an undirected weighted graph of 30 corridors and 27 nodes. The cost function is not distance — it blends distance, risk and accessibility, so "shortest" means "best" under a stated policy.

traversalCost = lengthKm × (1 + α × riskScore/100) + accessibilityPenalty + incidentPenalty

An array-scan priority queue rather than a binary heap: at tens of nodes the heap's bookkeeping costs more than it saves, and the code stays readable.

Penalty-method k-alternative paths
convex/lib/routeGraph.ts · findRouteOptions

Solve, multiply the winning path's edge costs by four, solve again, repeat. Produces genuinely different alternatives cheaply.

This is not Yen's algorithm and does not guarantee the true k-shortest set. It is bounded, cheap and reliably yields routes that differ by more than one segment — which is what an operator needs. Stated in the source rather than glossed over.

Connected components (depth-first search)
convex/lib/routeGraph.ts · reachableFrom

Distinguishes two failure modes that demand opposite responses: severed (a path exists but every route to it runs through a blocked segment — wait for clearance) versus disconnected (the two locations were never joined in the data — this route never existed). Collapsing both into "no route found" would tell an operator nothing.

Geospatial

Haversine great-circle distance
convex/lib/helpers.ts · haversineKm

Powers incident-influence radius, vehicle exposure and nearest-node resolution. Straight-line, and the report says so wherever the number is used — see §09.

d = 2R · asin(√(sin²(Δφ/2) + cos φ₁ · cos φ₂ · sin²(Δλ/2)))
Forward azimuth (initial bearing)
convex/lib/helpers.ts · bearingDegrees

Rotates each vehicle marker to its direction of travel, so heading reads without opening a popup.

Grid-bucket spatial clustering
src/lib/cluster.ts · clusterPoints

Cell size halves per zoom level, so a cell stays roughly constant on screen; clusters sit at the centroid of their members rather than the cell centre, so a two-point cluster does not visibly jump away from either point. Dependency-free — leaflet.markercluster has no maintained React 19 binding.

Quadratic Bézier curve generation
convex/lib/helpers.ts · curvedLine

Real mountain roads are never straight. Offsetting the midpoint perpendicular to the chord produces a believable arc for demonstration geometry, stored as a GeoJSON LineString so real OSM polylines replace it without a schema change.

Risk scoring

Weighted additive model with capped factors
convex/lib/riskCalculations.ts · calculateOverallRisk

Six factors whose caps sum to exactly 100, so a factor's cap is its maximum share of the score — which is what lets a contribution bar be read as a percentage.

rainfall 30 · incidents 20 · terrain 15 · road 15 · weather 12 · historical 8 = 100
Piecewise-linear rainfall response
convex/lib/riskCalculations.ts · calculateRainfallRisk

Band boundaries follow IMD's own rainfall classification — heavy at 64.5 mm, very heavy at 115.5 mm, extremely heavy at 204.5 mm — compressed into the 0–30 budget. Rainfall dominates deliberately: rainfall-triggered slope failure is the primary disruption mechanism in this region during monsoon.

Linear distance decay
convex/lib/riskCalculations.ts · calculateIncidentRisk

Incident influence falls linearly to zero at 30 km. The nearest and most severe incident dominates; each additional one contributes a quarter of its value, so a cluster scores higher than a single event without the total running away.

value = severityPoints × max(0, 1 − distanceKm / 30)
Logarithmic diminishing returns
convex/lib/riskCalculations.ts · calculateHistoricalRisk

The first repeat incident at a location is the most informative; the tenth adds little.

points = min(8, 3 + log₂(n) × 2.5)
Exponential smoothing (EWMA)
convex/lib/riskCalculations.ts · calculateOverallRisk

The raw score is blended 85 / 15 with the previous score so one noisy observation cannot flip a corridor between bands and back. Because it is a weighted average rather than an accumulation, it converges on the true value instead of ratcheting upward.

score = 0.85 × raw + 0.15 × previous
Deterministic safety envelope
convex/riskEngine.ts · confirmedStatusFromIncidents

A confirmed critical incident forces the road to blocked at score 100 regardless of what the model says. A landslide on the carriageway is not a probability. The road-condition factor is also derived from confirmed incidents rather than the road's stored status — feeding the engine's own output back in would create a ratchet that never releases.

Three-component confidence
convex/lib/riskCalculations.ts · calculateConfidence

Coverage (how many of five inputs were available), freshness (age of the weather observation) and agreement (how concentrated the contributions are — one dominant factor is a clearer signal than six small ones).

confidence = clamp(35 + 30·coverage + 18·freshness + 17·agreement, 35, 95)

Capped at 95 deliberately: a rule engine over partial data should never claim certainty.

Analytics & assistant

Composite operational health score
convex/lib/analytics.ts · calculateOperationalHealth

Same shape as the risk engine — six components whose caps sum to 100, each a ratio of real counts with a stated explanation. Road accessibility 25, delivery performance 20, incident load 20, vehicle availability 15, critical alerts 10, predicted risk 10.

Fixed-width time bucketing
convex/lib/analytics.ts · bucketTimestamps

Twelve buckets for 24 h, seven for a week, fifteen for a month — so a trend's shape is comparable between ranges rather than an artefact of bin count.

Ordered rule intent classification
convex/lib/intents.ts · classifyIntent

Keyword and pattern matching over an ordered, most-specific-first rule set, so "delayed critical deliveries" resolves to deliveries rather than vehicles. This is not natural language understanding, and when a question falls outside the fixed set it says so rather than guessing.

Stable-key deduplication
riskEngine · fleet · routeIntelligence

Every alert carries a stable identity — risk:<location>:<band>, delivery:<id>:delayed, route:<vehicle>:disrupted. An active alert with the same key suppresses a duplicate; a band change retires the stale one first. Verified: running detection twice raises 1 then 0.

06

Real-time design

There is no real-time code in this project. That is the point.

Convex tracks which documents a query read. When any of them change, it re-runs the query and pushes the new result to every subscribed client. So the entire real-time behaviour is a consequence of writing normal queries — no WebSocket server, no subscription registry, no cache invalidation logic, no socket.emit.

What this buys, concretely

  • The nine dashboard KPIs come from one query, so they share a single consistent snapshot and cannot disagree with each other mid-update.
  • Each answer in the assistant transcript holds its own subscription, so a two-minute-old answer updates if the situation changes — a stale answer on an operations console is worse than no answer.
  • Opening the dashboard in two browser windows and firing the demo shows both moving together. That is the single most convincing thing to show a judge, and it required no code.
The one place this does not apply

Convex actions — used for the outbound AI call, because they can reach the network — are not reactive. An AI answer is therefore a snapshot of the moment it was asked, and the UI labels it as such rather than letting it look live.

07

Does it work offline?

No

Not in the full sense, and the app never claims otherwise

The platform requires connectivity to function. What exists is a deliberately scoped subset that prevents data loss — not offline operation.

What genuinely works without a connection

CapabilityStatusDetail
Installable to home screenWorksWeb App Manifest, standalone display, launches at /field
Offline detectionWorksSurfaced as an explicit banner; the submit button disables
Draft preservationWorksEvery keystroke persisted to localStorage; restored on return, and across tabs
Offline shell cachingAbsentNo service worker — a reload while offline fails
Queued mutations / background syncAbsentConvex mutations do not queue and replay; a report must be submitted online
Offline map tilesAbsentTiles are fetched from the network on demand
Why we did not fake it

A field officer in a valley with no signal, shown a green "Report sent" that never left the device, is worse off than one shown an honest failure — they believe help is coming. So there is no optimistic "sent" state anywhere: a report is only ever marked submitted once the mutation returns a database id.

What full offline would take

The schema is already prepared for it. incidents.clientUuid exists precisely so a replayed report cannot create a duplicate, and incidents.deviceTs preserves observation time separately from arrival time. Completing it needs three additions: a service worker for the app shell, an IndexedDB write queue, and a Background Sync registration to drain that queue on reconnect. Roughly a day of work — deliberately not claimed as done.

08

Judge questions

The questions most likely to be asked, and answers that hold up. Where an answer concedes a limitation, concede it first — volunteering it reads as rigour, being caught hiding it reads as fabrication.

Is this actually AI, or just if-statements?

It is a transparent weighted rule engine, and we say so on the screen. The status chip reads "Rule engine active", not "AI engine active", and the engine version is displayed next to it.

Here is why that is the right choice rather than a shortfall: a supervised model needs a labelled history of road closures for the NER, which is not publicly available. Fabricating one and calling the output "AI" would be dishonest, and a judge who probes would find it. What we built instead is auditable — every one of the six factors has a cap, a real data source, and a plain-language sentence explaining its contribution.

The ML path is prepared, not pretended. calculateOverallRisk is a pure function from a flat feature vector to a scored result; a Python service replaces exactly that one call and nothing else in the application changes.

Show me a risk score and tell me where it came from.

Open AI Risk Intelligence and select Seppa. It scores 90/100, and the panel decomposes it: rainfall 28.4 of 30 ("172 mm in 24h — extremely heavy, past the IMD threshold"), nearby incidents 18 of 20 ("confirmed landslide, critical, 3 km away"), road condition 15 of 15, terrain 13.8 of 15 ("steep high-altitude slopes, index 0.92"), weather 12 of 12, historical 3 of 8.

Those sum to 90.2. Because the six caps sum to exactly 100, each bar is readable as a percentage of the whole.

Is this real GPS navigation?

No — it is corridor-level path selection, and the distinction matters. The graph has 27 nodes; each edge is an entire highway between two towns, not a street. It answers "which corridors should this consignment use", never "turn left in 200 metres".

We also compute no travel times, because there is no speed data to derive honest ones from. Distance and a weighted cost, yes; an ETA in minutes, no.

What happens when a road is blocked — does it just get a higher score?

No. A blocked segment is removed from the graph entirely, not penalised. A closed road is not an expensive option; it is not an option. Trigger the landslide in the demo console and watch the direct Guwahati→Shillong route vanish from the results, leaving only the Nongpoh alternative.

Why does it recommend a longer route?

Because delivery priority changes the cost function. For a critical consignment, Guwahati→Shillong recommends the 67 km two-segment route over the 65 km direct one — the direct corridor is restricted at risk 68 versus 41. The panel states the reason: "average corridor risk is 27 points lower than the next option".

The risk coefficient α scales from 1.0 for a routine load to 3.0 for an emergency one, so an ambulance accepts far more distance to avoid risk than a routine truck does.

How do you stop the alert centre filling with duplicates?

Every alert carries a stable dedupeKey. An active alert with the same key suppresses a new one, and when a risk band changes the stale alert is resolved before the new one is raised — so the centre tracks the current situation rather than accumulating history.

Demonstrable: run route-disruption detection twice and it raises 1, then 0.

Does it work offline? Field officers have no signal.

Not fully, and that is the honest answer. Drafts are preserved on the device and connectivity is surfaced clearly, so nothing typed is ever lost. But Convex mutations do not queue, there is no service worker, and map tiles need the network.

Critically, there is no false "sent" confirmation — a report is marked submitted only when the database returns an id. In the field, a false confirmation is worse than an honest failure. The schema already carries clientUuid for the sync work; see §07.

Is the data real?

Mixed, and separable. Real: district-headquarter coordinates, National Highway designations (NH-6, NH-13, NH-10, NH-37), the eight states and their districts, IMD rainfall classification thresholds, and the terrain profile of each location.

Demonstration data: the specific incidents, vehicles, consignments and the monsoon scenario. Road geometry is representative — a curve between two real endpoints, not a surveyed centreline. The schema stores GeoJSON so real OSM geometry drops in without a migration.

Why Convex and not a normal backend?

Because the real-time requirement disappears. Convex tracks which documents a query read and re-runs it when they change — so a WebSocket server, a subscription registry and cache-invalidation logic all become unnecessary. That is roughly four moving parts removed from the deployment.

The trade-off is honest: we are coupled to a managed platform, and heavy graph work runs in the query layer rather than a specialised engine. At this scale that costs nothing measurable.

How would this scale beyond a demo?

Three known pressure points, each with a named fix. The dashboard aggregate scans tables — past a few thousand documents it moves to an incrementally-maintained counts table. The route graph is rebuilt per query — it becomes a cached materialised structure invalidated on road change. Vehicle exposure is O(vehicles × hazards) — it becomes a spatial index.

None is architectural; all three are localised.

Where are your API keys?

There are none in the client. The map basemap needs no key at all. The optional AI key lives in a Convex environment variable and is read only inside a server-side action; .env* is gitignored. The only public value is the Convex deployment URL, which is a public identifier by design.

What was the hardest bug?

A good one to have ready. The road network initially had six disconnected components — most origin–destination pairs were unreachable and no alternative existed anywhere, so routing was impossible regardless of the algorithm. We diagnosed it with a connected-components pass before writing any pathfinding, then added nine real NER corridors (Silchar–Imphal, Aizawl–Silchar, Agartala–Silchar, Nagaon–Dimapur and others) to bring it to two.

The remaining isolated component is Sikkim — and that is geographically correct: it connects to India via Siliguri in West Bengal, outside the monitored region. We left it isolated and made the engine explain it rather than faking a link.

09

Limitations

Stated plainly, because a system intended for authorities should be auditable — and because volunteering a limitation is what makes the rest of the claims credible.

Intelligence

Rule engine, not machine learning

No trained model. Terrain and flood indices are documented static baselines pending DEM and CWC integration. The integration point is a single pure function.

Routing

Corridor-level, no travel times

27 nodes, each edge a whole highway. No turn-by-turn, no ETA in minutes — there is no speed data to derive one honestly.

Geospatial

Straight-line proximity

Vehicle exposure uses great-circle distance, not road-network distance. It deliberately over-triggers: a false flag is cheap, a missed vehicle entering a closed corridor is not.

Coverage

Sikkim unroutable

Correct, not a defect — it connects via West Bengal, outside the monitored network. The engine distinguishes this from a closure.

Offline

Draft preservation only

No service worker, no queued mutations, no offline tiles. See §07 for exactly what works and what completing it would take.

Security

No authentication

Roles are stored and editable but do not gate access. The schema carries tokenIdentifier so a provider drops in without a migration.

Data

Representative geometry

Real endpoints and real NH numbers; the centrelines between them are generated curves, not surveyed alignments.

Assistant

Fixed question set

Keyword matching over ~13 intents, not language understanding. Unrecognised questions are refused rather than guessed at.

The standing rule

No feature in this system is presented as working when it is not. Every limitation above is stated in the product itself — in the status chips, the panel footers and the popup text — not only in this document. That consistency is deliberate: it is what lets everything else on screen be taken at face value.
